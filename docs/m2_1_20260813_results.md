# M2.1 native LLaDA2 route-opportunity result

Date: 2026-08-13

Status: **COMPLETE — PRIMARY HYPOTHESIS NOT SUPPORTED; PROJECT CLOSED**

## Scope

This result measures stock `inclusionAI/LLaDA2.0-mini` native denoising routes. It is
supporting route evidence, not EP timing, text-quality evidence, or a speedup result.

```text
model revision       dad945cac317da394b390f82c7b40691d8a881ed
GPU                  NVIDIA H100 PCIe 80 GB
PyTorch / CUDA       2.6.0+cu124 / 12.4
Transformers         4.57.1
workloads            reasoning, code, general
seeds                17, 29, 41
requests/segment     32
block / steps        32 / 32
generation length    128 (four blocks)
temperature          0
```

The collection contains nine independent workload/seed segments, 288 generated
requests, 4,334 microbatch-step route arrays, and 493 complete fixed-pool observations
eligible for request-composition comparison. All 288 requests completed with zero
remaining mask tokens.

The raw bundle is 1.6 GB and remains outside Git. Its metadata records SHA-256 hashes
for all six data artifacts. The copied local files match every recorded hash.

A full-array audit also passed: all 4,334 route arrays have the expected 19 sparse
layers and top-8 cardinality, expert IDs span the valid `0..255` range, no top-k group
contains duplicate experts, all routing weights are finite and nonnegative, and the
maximum FP16 error in the expected 2.5 selected-weight sum is 0.00111.

## Compatibility correction found by the smoke test

The pinned checkpoint requires an explicit attention-mask batch dimension equal to the
runtime input batch. The collector originally supplied `[1, 1, S, S]`; the smoke test
correctly failed against an eight-request microbatch. The collector now expands the
same block-causal mask to `[B, 1, S, S]`. A regression test covers this requirement.

This correction changes neither permitted attention edges nor denoising semantics.

## Route-space result

The planner objective is:

```text
sum over batch and sparse layer of max destination-rank assignment load
```

The current-route plan is a 64-restart best-found diagnostic plan, not an exact oracle.
The previous-step plan uses only the immediately preceding observed route and is
evaluated on the current route.

| Expert placement | Complete cells | Positive headroom | Best-found median | Best-found P25 | Previous-route capture median | Capture P25 | Formal status |
|---|---:|---:|---:|---:|---:|---:|---|
| Contiguous | 493 | 78.90% | 0.0430% | 0.0067% | 100.00% | 83.02% | `PREVIOUS_ROUTE_PASS` |
| Round-robin | 493 | 80.73% | 0.0529% | 0.0103% | 94.61% | 71.04% | `PREDICTION_GAP` |

The maximum best-found objective reduction observed in any cell was 0.4797% for
contiguous placement and 0.4828% for round-robin placement. Positive cells are common,
but their magnitude is very small.

The analyzer's formal aggregate status is:

```text
ROUTE_SPACE_MAPPING_OR_PREDICTION_DEPENDENT
```

That label describes estimator capture conditional on nonzero best-found gain. It must
not hide the more important magnitude result.

## Correlation and placement observations

Across workload classes, median adjacent-step per-position route Jaccard is about
0.91, and median within-request temporal signature cosine is above 0.999. The median
within-request minus between-request signature cosine is positive but small:

| Workload | Masked-position spatial Jaccard | Temporal position Jaccard | Within-request temporal cosine | Between-request cosine | Difference |
|---|---:|---:|---:|---:|---:|
| Code | 0.2777 | 0.9154 | 0.9993 | 0.9645 | 0.0343 |
| General | 0.2618 | 0.9111 | 0.9993 | 0.9555 | 0.0422 |
| Reasoning | 0.2576 | 0.9119 | 0.9993 | 0.9659 | 0.0332 |

The model activates all 256 routed experts in the median observation. Route persistence
is high, but requests are also similar to one another. That combination explains why
previous-route prediction can be accurate while request recomposition has little room
to improve the batch objective.

Expert placement changes projected rank imbalance more than request composition does:

| Placement | Median projected max/mean rank load | P95 |
|---|---:|---:|
| Contiguous | 1.0743 | 1.1211 |
| Round-robin | 1.0407 | 1.0656 |

This is route-space evidence only. It does not prove an equivalent wall-clock benefit.
It shows that request composition is too weak a control variable in the measured
workload to justify continued investment under the existing hardware target.

## Decision

The pre-existing hardware target MDE is 2%. Every observed best-found route-objective
reduction is below 0.5%. Gate 2B previously left the proxy-to-time transfer unresolved,
so these load fractions are not converted into a claimed latency bound. Nevertheless,
the current evidence does not justify another paid scheduler-timing run:

```text
request-composition scheduler timing at M2.2    NO-GO
native-model speedup claim                      NOT AUTHORIZED
generic absence of all scheduling opportunity  NOT CLAIMED
```

The 2% magnitude disposition was not part of the original route-only 80% estimator
criterion. It is recorded explicitly as a post-measurement budget decision based on the
already existing hardware MDE, not presented as a preregistered M2.1 statistical gate.

This result closes RefineServe's primary request-composition hypothesis. Expert
placement, native active-width behavior, and position-level scheduling are different
hypotheses and are not adopted as follow-on milestones in this repository. M2.2, the
full true-EP adapter, and upstream integration are deferred indefinitely. See the
[project closure](project_closure.md).
